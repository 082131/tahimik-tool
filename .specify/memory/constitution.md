# TAHIMIK Constitution

## Core Principles

### I. Branch Discipline

`main` MUST always be in a working state, which means two checkable things:
CI is green (`pytest` on Python 3.10 and 3.11), and a synthetic-noise run
started from `main` at `seed = 42` reproduces its previous output. The second
clause is currently unverified by any test; adding that test is required work,
not optional.

Nothing is committed to `main` directly. Every change lands on a branch named
`<type>/NNN-<short-description>` — for example `feat/001-noise-estimator` —
and reaches `main` only through a reviewed pull request.

Permitted types: `feat/`, `fix/`, `docs/`, `test/`, `refactor/`, `exp/`,
`ci/`, `chore/`.

Every branch carries a number, including branches with no spec behind them.
The next number is one above the highest already used in either `specs/` or
any existing branch name, checked by hand. Spec Kit derives its own numbering
from `specs/` directories alone and will therefore reuse a number already
taken by an unspec'd branch; when that happens the human number wins and the
spec directory is renamed to match.

`exp/` branches are exempt from the spec loop and from nothing else. An
experiment obeys the reproducibility, testing, and history rules in full. The
prefix signals "may never merge", not "may be sloppy" — an experiment that
produces a number worth reporting must already be traceable when it does.

`main` carries no GitHub branch protection: the repository is private on the
free tier, where protected branches are unavailable. There is no safety net
behind this principle, which is precisely why it is absolute rather than
best-effort.

### II. Spec-Driven Development (NON-NEGOTIABLE)

Features are not built from a prompt. Each is interrogated first, the answers
become a spec under `specs/NNN-name/`, and the spec is what gets built
against — never the reverse. The sequence, and which tool owns each step, is
defined in `docs/SPEC-WORKFLOW.md` and is binding.

**Scope.** A spec is required for every `feat/` branch and for any change to
`src/models/` or `src/training/`, whatever the branch type. Fixes, docs, CI,
chores, and refactors elsewhere go straight to a branch and a PR. The loop
exists to protect the thesis contribution; applying it to a typo fix would
turn it into ritual, and rituals get skipped.

**No invented answers.** No one — human or AI assistant — invents an answer to
an open design question. If a spec is silent on why a component behaves a
particular way, the correct action is to ask, or to record the gap as
`NEEDS CLARIFICATION`. A plausible guess is worse than a blank: a blank gets
noticed, a guess gets defended as though it were a decision.

**Retrofitting.** A spec MUST describe what a component *should* do, written
as though the implementation did not exist. Reading the code and transcribing
it into spec form is prohibited — it yields a spec that agrees with every bug
the code happens to contain.

**Divergence.** When `/speckit-converge` reports a task as "done differently
than specified", neither side wins automatically. The divergence is
investigated and resolved as an explicit decision — a bug in the code, or a
design choice whose reasoning was never written down — and the resolution is
recorded in the spec either way. Silently amending the spec to match the code,
and silently rewriting code to match a spec authored after the fact, are both
prohibited.

**Open questions.** A spec MAY merge with unresolved `NEEDS CLARIFICATION`
markers, because some questions are genuinely blocked on the gold-standard
dataset or on adviser input, and holding the spec hostage helps nobody. No
task that depends on an open question may be implemented until it is closed.
Documented and ready-to-build are different states.

### III. Reproducibility (NON-NEGOTIABLE)

The contribution is a controlled comparison of three variants under identical
conditions. That comparison means nothing if its control variables are not
fixed and traceable.

**Where settings live.** Anything that alters model output lives in
`configs/`, never inline and never as a runtime flag. `--device`,
`--output_dir`, and `--batch_size` are operational and may remain flags.
`--num_beams` and `--seed` currently exist as flags in `scripts/` and MUST be
moved into `configs/`. A change to `configs/base.py` affects all three
variants and MUST be called out explicitly in the commit message.

Batch size is a known edge case: it does not change the model, but in
evaluation it changes padding within a batch and can shift generated output.
It stays operational for now; if reported numbers ever look unstable, it is
the first thing to pin.

**Seeds and determinism.** `seed = 42` is fixed unless a change is
deliberately testing seed sensitivity, stated in the commit message. Seeding
alone does not make GPU execution deterministic, because cuDNN kernel
selection and non-deterministic reductions vary between runs on the same seed.
The project therefore enables PyTorch deterministic mode —
`torch.use_deterministic_algorithms(True)`, the cuDNN deterministic flags, and
the required `CUBLAS_WORKSPACE_CONFIG` — so that a run reproduces bit-for-bit
from the same commit and seed. That is the target and the default.

Some operations have no deterministic implementation and raise an error under
this setting. When that happens, the operation is replaced with a
deterministic equivalent. If none exists, the exception is documented at that
call site with the reason, and any result produced through it reports the
variance observed across runs. Bit-exact reproduction is the rule; a
documented tolerance is the narrow, named exception, never the default.

**Traceability.** Every results file MUST carry the git SHA that produced it,
a flag indicating whether the tree was dirty, and the fully resolved
configuration actually used, including any overrides. This is stamped by the
scripts, not recorded by hand — traceability that depends on remembering is
traceability that fails at exactly the moment a number gets exciting.

**Efficiency claims.** No efficiency number — GPU memory, latency, deletion
rate — enters the manuscript without a committed results file from a benchmark
run traceable to a commit. CI runs on CPU and cannot produce these.

**Code that contradicts the manuscript.** Wherever a configuration value
disagrees with what the manuscript states, the code carries a comment at that
line saying so and naming which is authoritative. `configs/base.py` pins
`google/byt5-small` while the manuscript specifies `byt5-base` for the
experiments; that is the known instance today, and the rule exists to catch
the ones not yet found. No reported result may come from a run whose config
contradicts the manuscript unless that divergence is stated alongside it.

### IV. Test-First & CI Gate

`python -m pytest tests/ -v` MUST pass before any change is proposed for
merge. The suite runs automatically on every push and pull request via
`.github/workflows/tests.yml` on Python 3.10 and 3.11. A red check blocks
merge regardless of who or what authored the change.

**Test-first is mandatory for `src/models/` and `src/training/`.** That is the
code a panel questions hardest, and it is written red-green-refactor.
Elsewhere tests are required but their order is not mandated.

**When fixing a bug anywhere**, the regression test is written first and
confirmed to fail against the broken code before the fix exists. A regression
test that never observed the bug it claims to guard proves nothing.
`tests/test_delete_gate.py` is the standing example.

CI cannot exercise GPU behaviour. Correctness is proven on CPU; efficiency is
proven by recorded benchmark runs under Principle III.

### V. Transparent AI Assistance & Clean History

Parts of this repository are written with AI assistance. That is declared, not
hidden.

Every commit made with AI assistance carries a `Co-Authored-By:` trailer
naming the model, and that trailer is never stripped. Beyond the trailer, the
repository carries `docs/AI-USE.md` stating which tools were used, for what,
and pointing at the specs and commit trailers as evidence. Examiners read
documents; they do not run `git log`. The trailer is the proof; the document
is what makes the proof findable.

History stays auditable:

- **Merge commits, never squash.** Squashing destroys the per-commit reasoning
  that makes this history worth reading. No tool default and no future
  collaborator may change this.
- **Branches are deleted by hand** after merge, by whoever merged. GitHub's
  auto-delete setting stays off: deleting a branch is a decision, not a
  default.
- **One logical change per commit**, with a message explaining *why*. The diff
  already shows what.
- **Secrets, datasets, checkpoints, and dependency trees are never committed.**
  All are gitignored. `git status` is checked before staging, and anything
  unexpected is investigated before it is added.

## Technology & Data Constraints

Python, with 3.10 and 3.11 both exercised in CI. The comparison is built on
ByT5 and MrT5, served by a FastAPI backend (`backend/`), with a React/Vite
demo frontend (`frontend/`) and a separate annotator application
(`annotation-platform/`).

**This constitution governs the entire repository, with no carve-outs.** The
branch, review, testing, and history rules apply to the frontend and the
annotation platform exactly as they apply to `src/`. The reproducibility rules
bind wherever results are produced, which in practice means the research code.

The gold-standard dataset and the annotation platform that produces it are
still under active development. Retrofitting specs onto the annotation
platform is deferred until its shape settles — specifying something that
changes weekly produces a document that is wrong on arrival. This defers
*retrofitting only*: new `feat/` work in that directory follows the spec floor
in Principle II like anything else.

No raw datasets, trained checkpoints, or dependency trees are ever committed,
regardless of how small or how "just this once" a given file appears.

## Development Workflow

**Review.** At least one groupmate approves a pull request before it merges.
Changes under `src/models/` or `src/training/` require a reviewer who can
check the maths. If no review arrives within 48 hours, the author may
self-merge and MUST record in the PR that they did so and why. The timeout
exists to prevent deadlock; reaching for it routinely means the review rule
has failed and should be renegotiated rather than quietly ignored.

**Tool division is fixed, not a matter of taste.** `/grill-me` for
interrogation; spec-kit (`/speckit-specify`, `/speckit-clarify`,
`/speckit-plan`, `/speckit-tasks`, `/speckit-converge`, `/speckit-analyze`)
for artifacts; `/tdd` for building. `to-spec`, `to-tickets`, `triage`, and
`wayfinder` are deliberately unused — a second artifact tree describing the
same features is worse than one source of truth.

**PR bodies** answer three questions: what problem this solves, how it was
verified, and what reviewers should look at closely.

## Governance

This constitution supersedes ad hoc practice. Where it conflicts with a habit,
a template default, or a tool's suggestion, the constitution wins.

**Amendments** follow the same path as any other change: a branch, a pull
request, one approval. The PR body states the version bump and the reasoning.
No special ceremony — a governance process heavier than the work it governs
gets routed around.

**Versioning** is semantic, applied to this document:

- **MAJOR** — a principle is removed, or redefined incompatibly with prior
  guidance.
- **MINOR** — a principle or section is added, or guidance materially
  expanded.
- **PATCH** — wording, clarification, or typo fixes with no semantic change.

**Compliance.** Every PR is expected to be consistent with these principles. A
reviewer who spots a violation treats it as they would a failing test.
`CONTRIBUTING.md` and `docs/SPEC-WORKFLOW.md` carry the day-to-day mechanics
this document governs — read them alongside it, not instead of it.
